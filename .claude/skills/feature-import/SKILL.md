# feature-import

분석 방법은 rea가 설치한 `reverse-engineer-anything` 스킬을 따른다. 이 스킬은 결과를 어디에, 어떤 형식으로 남기는지만 정한다.

## 절차
1. 대상, 버전, 라이선스를 확인한다. 오픈소스, 내 소유, 분석이 허용된 프로그램만 다룬다. 아니면 멈추고 사용자에게 알린다.
2. 소스 저장소가 공개된 대상은 rea 없이 그 소스를 읽는다. rea는 배포된 앱·바이너리·웹사이트처럼 소스가 없을 때 쓴다. 이유: rea 스킬도 일반 소스 분석에는 rea를 쓰지 말라고 한다. 사용자가 고른 기능 범위만 분석한다. 범위가 불분명하면 rea로 기능 목록만 뽑아 보여 주고 고르게 한다.
3. 아래 형식으로 정리한다.
   - plan mode라면 plan 파일의 `## 참고 분석` 절에 쓴다. 승인 후 첫 작업으로 `docs/research/<대상>-<기능>.md`에 옮긴다. plan mode에서는 plan 파일만 쓸 수 있기 때문이다.
   - plan mode가 아니면 바로 `docs/research/<대상>-<기능>.md`에 저장한다.
4. 대상의 코드와 문자열 원문(소스, UI 문구, 식별자)은 우리 코드로 옮기지 않는다. 행동만 우리 말로 적는다. research 문서에 근거로 다는 모듈·라우트 이름과 `관찰된 예시`의 입력·출력 값은 확인용이라 적어도 된다. 이유: 라이선스 위반이 되고, 남의 구조가 우리 ARCHITECTURE에 섞인다.

## 형식
```markdown
# <대상> — <기능>
## 대상
프로그램, 버전, 라이선스, 분석한 입력(앱 경로·HAR 등)
## 가져올 기능
사용자가 고른 범위. 빼기로 한 것도 적는다.
## 행동
입력 → 처리 흐름 → 출력 → 에러. 각 줄에 rea 근거(모듈·라우트 이름 수준)를 단다.
## 관찰된 예시
입력/출력 쌍. 인수 테스트 재료가 된다.
## 모르는 것
rea가 unknowns로 남긴 것, 정적 분석으로 확인하지 못한 것.
```

## 다음 단계
- `## 모르는 것`은 검증 안 된 가정이다. 사용자에게 묻거나 확인 step을 먼저 둔다(`/harness` B절).
- `## 관찰된 예시`는 고정 AC 인수 테스트로 옮긴다(`/harness` C절 9번).
- 이 기능을 다루는 step의 `## 읽어야 할 파일`에 research 문서를 넣는다.
